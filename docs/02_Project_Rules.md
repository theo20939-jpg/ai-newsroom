# **1. Цель документа**

Данный документ определяет обязательные инженерные правила проекта AI Newsroom.

Любой код, архитектурное решение, AI-модуль или новая функция должны соответствовать этим правилам.

При возникновении противоречий между скоростью разработки и настоящим документом приоритет всегда имеет данный документ.

# **2. Главные принципы проекта**

# **2.1 Качество важнее скорости**

Запрещается писать код “на время”.

Любая реализация должна быть рассчитана на дальнейшее развитие.

MVP может содержать упрощённую логику, но архитектура должна оставаться масштабируемой.

# **2.2 Один модуль — одна ответственность**

Каждый сервис отвечает только за одну задачу.

Например:

- Collector собирает новости.
- Analyzer анализирует.
- Copywriter пишет тексты.
- Meme Engine создаёт мемы.

Запрещается объединять несколько бизнес-задач в одном сервисе.

# **2.3 Модули независимы**

Любой сервис должен быть заменяемым.

Замена модели ИИ или алгоритма не должна требовать переписывания других модулей.

# **2.4 AI — часть архитектуры, а не бизнес-логики**

Промпты, настройки моделей и вызовы AI отделяются от основной логики приложения.

Бизнес-логика не должна содержать текстов промптов.

# **2.5 Никакой магии**

Каждое решение должно быть объяснимым.

Если новость получила высокий рейтинг, система должна уметь объяснить, почему.

# **3. Архитектурные правила**

# **Backend строится по модульному принципу**

Каждый сервис имеет:

- собственную директорию;
- собственные интерфейсы;
- собственные тесты;
- собственную документацию.

Сервисы не должны обращаться друг к другу напрямую.

Взаимодействие осуществляется через заранее определённые интерфейсы или события.

Любая новая функция должна добавляться как отдельный модуль.

# **4. Правила написания кода**

# **TypeScript**

Используется строгий режим (strict).

Использование any запрещено.

Все функции должны иметь типизированные параметры и возвращаемые значения.

Любой публичный метод документируется.

Код должен быть максимально читаемым.

Предпочтение отдаётся понятности, а не сокращению количества строк.

Не допускается дублирование логики.

Повторяющийся код выносится в отдельные сервисы или утилиты.

# **5. Работа с AI**

Каждый AI-агент имеет одну конкретную задачу.

Примеры:

- анализ новости;
- написание поста;
- генерация мема.

Запрещается создавать одного универсального AI-агента, выполняющего множество функций одновременно.

Каждый AI-запрос должен иметь:

- чёткую цель;
- фиксированный формат входных данных;
- фиксированный формат ответа;
- обработку ошибок;
- повторный запрос при необходимости.

Все промпты хранятся централизованно.

Промпты являются частью проекта и имеют собственные версии.

Любая AI-модель должна заменяться без изменения бизнес-логики.

# **6. Работа с источниками данных**

Каждый источник реализуется как отдельный адаптер.

Добавление нового источника не должно требовать изменения существующих.

При невозможности получить данные из одного источника остальные продолжают работу.

Любой парсер обязан:

- логировать ошибки;
- повторять запрос;
- соблюдать ограничения источника.

# **7. Работа с базой данных**

База данных является единственным источником истины.

Запрещается хранить критичные данные только в памяти.

Все изменения данных проходят через сервисный слой.

Каждая сущность имеет:

- дату создания;
- дату изменения;
- уникальный идентификатор.

# **8. Работа с конфигурацией**

Все настройки находятся в .env.

Запрещается хранить:

- API-ключи;
- токены;
- адреса серверов;
- секреты

в исходном коде.

Любая новая настройка должна быть документирована.

# **9. Работа с Telegram**

Telegram является интерфейсом пользователя.

Вся бизнес-логика выполняется на сервере.

Бот отвечает только за взаимодействие с пользователями.

# **10. Работа с ошибками**

Ни одна ошибка не должна приводить к остановке системы.

Любая ошибка:

- логируется;
- классифицируется;
- при необходимости повторяется автоматически.

Пользователь получает понятное сообщение вместо технической ошибки.

# **11. Работа с логированием**

Каждый сервис ведёт собственный журнал.

Логируются:

- ошибки;
- время выполнения;
- обращения к AI;
- обращения к API;
- критичные события.

Логи должны позволять восстановить последовательность действий системы.

# **12. Работа с тестированием**

Каждый сервис тестируется независимо.

При изменении бизнес-логики обновляются соответствующие тесты.

Критичные алгоритмы должны иметь автоматические тесты.

# **13. Работа с производительностью**

Любая дорогая операция должна быть оправдана.

Предпочтение отдаётся:

- кэшированию;
- пакетной обработке;
- очередям;
- повторному использованию результатов AI.

Система не должна выполнять одинаковый AI-анализ дважды.

# **14. Работа со стоимостью**

Стоимость работы системы является одним из основных критериев качества архитектуры.

Перед использованием AI необходимо определить:

- можно ли решить задачу обычным кодом;
- можно ли использовать более дешёвую модель;
- можно ли использовать уже сохранённый результат.

Дорогие модели используются только тогда, когда это действительно повышает качество.

# **15. Работа с документацией**

Любая новая функция сопровождается документацией.

Документация обновляется одновременно с кодом.

Документация считается частью продукта.

# **16. Zero Technical Debt Policy**

В проекте запрещается сознательно создавать технический долг.

Если временное решение неизбежно, оно должно:

- быть явно отмечено;
- иметь описание причины;
- иметь план замены.

# **17. Принципы разработки**

При принятии любого решения команда придерживается следующих правил:

1. Простота важнее сложности.
2. Модульность важнее скорости.
3. Автоматизация важнее ручной работы.
4. Масштабируемость важнее локальной оптимизации.
5. Объяснимость важнее “магии”.
6. Надёжность важнее количества функций.

# **18. Definition of Done**

Любой модуль считается завершённым только если:

- реализована вся функциональность;
- написаны тесты;
- обновлена документация;
- обработаны ошибки;
- настроено логирование;
- соблюдены правила проекта;
- код соответствует архитектуре.

# **19. Правила работы с Claude Code**

Все задачи для Claude Code должны соответствовать следующим требованиям:

- Один промпт — одна задача.
- Запрещается просить Claude “сделать всё сразу”.
- Claude получает ссылки на актуальные документы проекта.
- Перед написанием нового модуля Claude использует существующие интерфейсы и не создаёт альтернативные реализации без необходимости.
- Любой сгенерированный код должен соответствовать настоящему документу.

# **20. Главный принцип проекта**

**AI Newsroom строится как долгоживущий инженерный продукт, а не как набор скриптов.**

# **21. Architecture Evolution Rules**

**Принципы эволюции архитектуры**

AI Newsroom проектируется как система, способная развиваться на протяжении многих лет без необходимости переписывания ядра приложения.

Любое новое решение должно проектироваться с учётом будущего расширения функциональности.

**21.1 Расширяемость**

Новые функции должны добавляться без изменения существующей бизнес-логики.

Предпочтение отдаётся расширению системы, а не изменению уже работающих компонентов.

**21.2 Plug-in Architecture**

Любой новый компонент должен подключаться как независимый модуль.

Это относится к:

- источникам данных;
- AI-агентам;
- генераторам контента;
- аналитическим сервисам;
- интеграциям;
- каналам публикации.

Добавление нового модуля не должно требовать изменения остальных компонентов системы.

**21.3 Adapter Pattern**

Все внешние сервисы подключаются исключительно через адаптеры.

Это правило распространяется на:

- Telegram;
- Reddit;
- RSS;
- Hacker News;
- GitHub;
- Product Hunt;
- OpenAI;
- Anthropic;
- Google AI;
- любые будущие интеграции.

Бизнес-логика не должна зависеть от конкретного API внешнего сервиса.

**21.4 AI Independence**

Каждый AI-агент работает через единый интерфейс.

Замена модели или поставщика AI не должна требовать изменений в логике приложения.

Например, система должна позволять безболезненно заменить одну модель другой (например, OpenAI на Anthropic или наоборот), если это потребуется по качеству, стоимости или другим причинам.

**21.5 Replace Instead of Rewrite**

Любой внутренний алгоритм должен быть заменяемым.

Если в будущем потребуется улучшить:

- алгоритм оценки новостей;
- поиск трендов;
- генерацию мемов;
- ранжирование контента;
- генерацию текстов,

новая реализация должна подключаться без переписывания остальных модулей.

**21.6 Future Content Types**

Архитектура должна предусматривать возможность добавления новых типов контента.

Например:

- изображения;
- видео;
- короткие вертикальные ролики;
- подкасты;
- инфографика;
- карусели;
- email-рассылки;
- сценарии для YouTube;
- другие форматы.

Каждый новый тип реализуется как отдельный генератор, использующий общую систему анализа новостей.

**21.7 Scalability by Design**

Даже если первая версия предназначена исключительно для личного использования, архитектура должна быть готова к росту.

Проект должен предусматривать возможность перехода от:

- одного пользователя;
- к небольшой команде;
- затем к нескольким редакциям;
- и при необходимости — к полноценному SaaS-продукту,

без изменения фундаментальных архитектурных принципов.

**21.8 Backward Compatibility**

При добавлении новой функциональности запрещается нарушать работу существующих модулей.

Изменения должны быть обратно совместимыми либо сопровождаться контролируемой миграцией.

**21.9 Evolution Over Revolution**

Развитие проекта должно происходить эволюционно.

Предпочтение всегда отдаётся постепенному улучшению существующих компонентов вместо полного переписывания системы.

Любая крупная переработка архитектуры должна рассматриваться только в случае, если дальнейшее развитие текущего решения объективно невозможно.

**Главный принцип эволюции проекта:**

**AI Newsroom должен расти за счёт добавления новых возможностей, а не за счёт переписывания уже работающих компонентов.**

## 22. Efficiency by Design

Система должна использовать **самый простой, быстрый и экономичный инструмент**, который способен решить задачу с требуемым качеством.

Использование больших языковых моделей (LLM) допускается только тогда, когда классические алгоритмы, статистические методы или эвристики уже не обеспечивают необходимый результат.

При проектировании любого нового модуля разработчик обязан ответить на следующие вопросы:

1. Можно ли решить задачу без использования AI?
2. Можно ли решить её с помощью обычных алгоритмов?
3. Можно ли использовать ранее сохранённый результат?
4. Можно ли использовать более дешёвую модель?
5. Только если ответы отрицательны — допускается использование более мощной LLM.

### AI is the Last Step

LLM рассматривается как специализированный эксперт, а не как универсальный инструмент.

Большая часть обработки данных должна выполняться детерминированными алгоритмами.

### Cost is a Feature

Стоимость обработки является полноценной метрикой качества архитектуры.

Любое новое решение должно учитывать не только качество результата, но и стоимость эксплуатации.
