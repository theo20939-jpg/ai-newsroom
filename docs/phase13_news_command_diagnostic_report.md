# Phase 13 — Диагностика команды /news после Phase 13

Только чтение. Ни один файл не был изменён. Ни один воркер не запускался. Живых вызовов
провайдера не выполнялось — только read-only SQL-запросы к уже существующим данным (включая
задачу, созданную во время M7).

## 1. `bot/handlers/news.py` — что вызывается, что запрашивается, какие статусы учитываются

**Какой сервис вызывается**: `services.editorial_inbox_service.get_latest_editorial_cards(session,
limit=5)` — единственный вызов бизнес-логики внутри хендлера (`bot/handlers/news.py:41`). Сам
хендлер — тонкая оболочка: открывает сессию, вызывает сервис, рендерит карточки
(`bot/formatting.render_editorial_card`), отправляет их. Никакой собственной query-логики в
хендлере нет — это явное архитектурное правило Phase 11 (Contract §9), подтверждённое
докстрингом файла.

**Какие записи запрашиваются** (`services/editorial_inbox_service.py:57-63`):

```python
stmt = (
    select(ContentDraft)
    .join(EditorialTask, ContentDraft.task_id == EditorialTask.id)
    .where(EditorialTask.status == TaskStatus.COMPLETED)
    .order_by(ContentDraft.created_at.desc(), ContentDraft.id.desc())
    .limit(limit)
)
```

Источник записей — **`ContentDraft`**, не `EditorialTask` и не `NewsEvent` напрямую.
`EditorialTask` и `NewsEvent` подтягиваются только как связанные данные для уже найденного
`ContentDraft` (`_to_card()` берёт `task.event_id` → `NewsEvent`, чтобы заполнить
`news_title`/`news_category`/`news_url`/`news_published_at` в карточке).

**Какие статусы учитываются**: только `EditorialTask.status == COMPLETED`. **Тип workflow
(`workflow_name`) нигде не фильтруется** — ни в `WHERE`, ни где-либо ещё. Это не проверка "покажи
только `CONTENT_GENERATION`" — фильтрации по типу workflow вообще нет в этом запросе.

## 2. Разрыв между `NEWS_ANALYSIS COMPLETED` и Telegram Editorial Inbox (`/news`)

Разрыв — не в фильтрации по `workflow_name` (её нет), а в том, что **запрос `/news` в принципе
устроен вокруг `ContentDraft`, а не вокруг `EditorialTask`**. `EditorialTask.status ==
COMPLETED` — необходимое, но не достаточное условие: строка попадает в выдачу `/news` только
если для неё **уже существует** связанный `ContentDraft` (через `JOIN`, а не `LEFT JOIN` —
задача без `ContentDraft` физически не может пройти этот `JOIN`).

`ContentDraft` создаётся ровно в одном месте кодовой базы — `services/content_draft_
service.py::ContentDraftService` (метод, создающий строку через `session.add(draft)`), а сам
этот класс конструируется только внутри `scripts/run_content_generation.py` — единственного
существующего вызывающего кода на весь репозиторий. `run_content_generation_for_event()` — это
ручной, не автоматический, не запланированный путь (Phase 10 Contract §9: "человек или внешний
процесс вызывает это вручную").

Phase 13 (`NEWS_ANALYSIS`) **сознательно и многократно задокументированно** не создаёт
`CONTENT_GENERATION`-задачи и не создаёт `ContentDraft` — это зафиксировано как замороженная
граница на каждом уровне (Architecture Contract, Implementation Plan §21/§22, все отчёты
M1–M7). Значит: `NEWS_ANALYSIS`-задача может дойти до `COMPLETED` сколько угодно раз — она
структурно никогда не создаст `ContentDraft` сама по себе, а без `ContentDraft` она никогда не
пройдёт `JOIN` в `get_latest_editorial_cards()`.

Итог: разрыв — не баг и не забытая фильтрация, а прямое следствие уже принятого архитектурного
решения ("Phase 13 останавливается на `NEWS_ANALYSIS COMPLETED`, без автоматического перехода к
`CONTENT_GENERATION`"), помноженное на то, что `/news` был спроектирован в Phase 11 **до**
Phase 13 и рассчитан ровно на один существующий источник данных (`ContentDraft` от ручного
`CONTENT_GENERATION`).

## 4. Ответ

**Почему `/news` сейчас не показывает результаты Phase 13**: потому что `/news` (Phase 11) читает
исключительно `ContentDraft`, а `ContentDraft` создаётся исключительно вручную, исключительно
через `CONTENT_GENERATION`-пайплайн (`scripts/run_content_generation.py`). `NEWS_ANALYSIS`
(Phase 13) намеренно останавливается на `COMPLETED`, никогда не создавая ни `CONTENT_GENERATION`-
задачу, ни `ContentDraft` — это зафиксированная, неоднократно проверенная аудитами граница, а не
пропуск. Оба факта вместе структурно гарантируют: результат `NEWS_ANALYSIS`, включая M7, не может
появиться в `/news` при текущей архитектуре — не из-за отсутствующего фильтра по статусу, а
из-за отсутствующего источника данных для этого пути.

**Какая минимальная архитектурная связь нужна дальше** (только диагностика, не решение — выбор
принадлежит будущей фазе, вне рамок этого отчёта):

Разрыв можно закрыть одним из двух принципиально разных путей — ни один не реализован здесь и не
подразумевается как принятое решение:

1. **Связать `NEWS_ANALYSIS COMPLETED` → `CONTENT_GENERATION` → `ContentDraft`** (продолжить
   существующую цепочку так, как она уже спроектирована в Phase 10) — либо автоматическим
   триггером, либо явной ручной командой "сгенерировать контент по этому анализу". Тогда `/news`
   продолжает работать без изменений — он и дальше читает только `ContentDraft`, просто эта
   таблица начинает наполняться и для событий, прошедших через `NEWS_ANALYSIS`.
2. **Дать `/news` (или отдельной команде) второй, независимый источник данных** —
   `EditorialTask.status == COMPLETED AND workflow_name == NEWS_ANALYSIS`, читаемый напрямую, без
   `ContentDraft` вообще. Это показывало бы результат аналитики (`engagement_potential_score`,
   `audience_fit`, `research`/`intelligence`-вывод) как отдельный тип карточки — не "готовый к
   публикации черновик", а "предсказанный потенциал/анализ", что семантически точнее отражает то,
   чем `NEWS_ANALYSIS` на самом деле является (Contract Phase 13: предсказание, не публикация).

Оба варианта требуют новой архитектурной работы (новый переход состояний либо новый
read-модель/новая команда) и явного решения человека, какой путь предпочтителен — этот отчёт
только фиксирует факт разрыва и его точную причину, не выбирает и не реализует решение.
