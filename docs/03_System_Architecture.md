# 1. Назначение документа

Данный документ описывает техническую архитектуру AI Newsroom.

Его цель — определить структуру системы, взаимодействие сервисов, жизненный цикл данных и инженерные принципы построения платформы.

Документ не описывает бизнес-логику отдельных модулей. Их функциональность раскрывается в документе **Functional Specification**.

---

# 2. Архитектурная философия

AI Newsroom строится как **модульная событийно-ориентированная AI-платформа (Modular Event-Driven AI Platform)**.

Основной принцип архитектуры:

> Каждый сервис отвечает только за одну задачу и может быть заменён без изменения остальных компонентов системы.
> 

Система проектируется так, чтобы:

- легко расширяться;
- легко масштабироваться;
- использовать различные AI-модели;
- добавлять новые источники данных;
- добавлять новые типы контента;
- работать как единое приложение или как набор независимых сервисов.

---

## Deterministic Layer

Deterministic Layer объединяет компоненты, работающие без использования LLM.

К ним относятся:

- Collector Service;
- Cleaning Service;
- Deduplication Service;
- Ranking Engine;
- Scheduler;
- Database Layer;
- Cache Layer;
- Monitoring;
- Telegram Service.

Эти компоненты выполняют все задачи, которые могут быть решены классическими алгоритмами.

Основная цель слоя — максимально сократить объём данных, передаваемых в AI.

---

## Intelligence Layer

Intelligence Layer состоит из специализированных AI-агентов.

Он получает только предварительно отобранные события и отвечает исключительно за интеллектуальные задачи:

- понимание смысла новости;
- объяснение её значимости;
- генерацию текстов;
- создание креативных материалов;
- контроль качества результата.

Использование AI для задач, которые могут быть решены Deterministic Layer, запрещается.

# 4. Основные сервисы

Архитектура состоит из независимых сервисов.

## Collector Service

Отвечает исключительно за получение информации из внешних источников.

Не анализирует данные.

Не принимает решений.

---

## Cleaning Service

Удаляет:

- рекламу;
- мусор;
- битые записи;
- служебную информацию.

---

## Deduplication Service

Определяет одинаковые новости.

Создаёт одну карточку события.

Хранит ссылки на все источники.

---

## Storage Layer

PostgreSQL является основным хранилищем проекта.

Все сервисы работают через единый слой доступа к данным.

---

## AI Analysis Engine

Проводит интеллектуальный анализ новости.

Определяет:

- категорию;
- важность;
- вероятность вирусности;
- основные темы;
- причины популярности.

---

## News Ranking Engine

News Ranking Engine является частью Deterministic Layer.

Он не использует LLM.

Основная задача — вычислить предварительный рейтинг каждой новости на основании объективных метрик.

### Используемые параметры

- количество просмотров;
- количество комментариев;
- коэффициент вовлечённости (ER);
- скорость роста активности;
- число независимых источников;
- авторитет источника;
- время публикации;
- тематика;
- язык;
- качество данных.

На основании этих параметров рассчитывается **Raw Score**.

Только новости, набравшие достаточный Raw Score, передаются в Intelligence Layer.

---

## Content Generator

Создаёт:

- сводки;
- посты;
- заголовки;
- идеи публикаций;
- мемы.

---

## Telegram Service

Единственная точка взаимодействия пользователя с системой.

# 6. Архитектура AI

AI в системе представлен не одной моделью, а набором специализированных агентов.

Каждый агент выполняет одну конкретную задачу.

Взаимодействие между агентами происходит через внутренние сервисы.

Подробная архитектура AI описывается в документе **AI Design Document**.

# 8. Очереди обработки

Все тяжёлые операции выполняются асинхронно.

Например:

- анализ AI;
- генерация мемов;
- поиск дублей;
- обновление статистики;
- повторный анализ.

Это позволяет не блокировать работу остальных сервисов.

---

## 9. Orchestrator Service

Orchestrator Service является центральным координатором системы.

Он не содержит бизнес-логики и не анализирует данные.

Его единственная задача — управлять жизненным циклом обработки каждой новости.

### Основные обязанности

- запуск процессов обработки;
- управление очередями задач;
- контроль последовательности выполнения сервисов;
- повторный запуск задач после ошибок;
- распределение нагрузки между AI-модулями;
- контроль завершения всех этапов обработки;
- управление расписанием обработки;
- запуск фоновых задач.

---

### Принцип работы

Каждая новость проходит обработку через Orchestrator.

Он определяет:

- какие сервисы должны быть вызваны;
- в какой последовательности;
- какие результаты необходимо дождаться;
- какие задачи можно выполнять параллельно.

---

### Orchestrator не имеет права

- анализировать новости;
- писать данные напрямую в Telegram;
- обращаться к AI;
- изменять бизнес-логику отдельных сервисов.

Он только управляет процессом.

---

### Преимущества

Использование Orchestrator позволяет:

- легко добавлять новые этапы обработки;
- масштабировать систему;
- заменять сервисы без изменения остальных компонентов;
- централизованно управлять очередями;
- контролировать ошибки;
- значительно упростить дальнейшее развитие проекта.

---

# 10. Кэширование

Все дорогие вычисления должны кэшироваться.

В первую очередь:

- AI-анализ;
- эмбеддинги;
- похожие новости;
- результаты генерации.

Запрещается повторно выполнять одинаковый AI-запрос без необходимости.

---

# 11. Работа с внешними сервисами

Все интеграции реализуются через адаптеры.

Каждый адаптер отвечает только за один источник данных.

В случае недоступности источника остальные сервисы продолжают работу.

---

# 12. Масштабирование

Архитектура должна поддерживать постепенное масштабирование:

- увеличение количества источников;
- увеличение количества новостей;
- подключение новых AI-моделей;
- добавление новых генераторов контента;
- поддержку нескольких проектов.

Масштабирование не должно требовать изменения архитектуры ядра.

---

# 13. Безопасность

Система не хранит секреты в коде.

Все ключи находятся во внешней конфигурации.

Любое взаимодействие с внешними сервисами должно учитывать лимиты API и механизмы повторных попыток.

---

# 14. Мониторинг

Каждый сервис обязан публиковать:

- статус работы;
- количество ошибок;
- время выполнения;
- количество обработанных объектов.

Все критические ошибки должны фиксироваться в централизованном журнале.

---

# 15. Отказоустойчивость

Ни один внешний сервис не должен иметь возможность остановить работу всей системы.

Если один компонент временно недоступен, остальные продолжают функционировать.

После восстановления соединения система должна автоматически продолжить обработку.

---

# 16. Жизненный цикл данных

Каждая новость проходит полный цикл:

Получение → Очистка → Дедупликация → Хранение → Анализ → Скоринг → Генерация контента → Публикация → Архив.

На каждом этапе сохраняются результаты обработки и история изменений.

---

# 17. Архитектурные принципы

При разработке системы соблюдаются следующие принципы:

- Modularity First
- AI First
- Event Driven
- API First
- Replaceable Components
- Explainable AI
- Cost Efficient AI
- Security by Design
- Scalability by Design
- Documentation First
- Orchestration First
- Asynchronous Processing
- Event Driven Pipeline

---

# 18. Будущее развитие

Архитектура должна позволять без изменения ядра:

- подключать новые источники;
- подключать новые AI-модели;
- добавлять новые форматы контента;
- подключать новые каналы публикации;
- внедрять новые алгоритмы оценки новостей;
- переходить к многопользовательскому режиму при необходимости.
